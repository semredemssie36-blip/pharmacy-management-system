STAGE 07 — DETAILED MODULE SPECIFICATIONS
PHARMACY MANAGEMENT / ERP SYSTEM
============================================================

PURPOSE
============================================================

This document provides detailed functional specifications for the
major modules of the Pharmacy Management / ERP System.

Stages 01–06 established:

- overall system purpose
- actors
- roles
- permissions
- data scope
- business workflows
- domain model
- database architecture
- technical architecture
- UX/UI architecture

Stage 07 now defines the actual functional behavior of each major
business module.

The purpose is to prevent the AI development agent from treating
the application as a collection of unrelated CRUD pages.

Every module must be understood as a business domain.

============================================================
CRITICAL AI AGENT RULE
============================================================

Before implementing any module, the agent MUST read:

Stage 01
Stage 02
Stage 03
Stage 04
Stage 05
Stage 06
Stage 07

The agent MUST NOT invent missing business rules.

If a requirement is unclear:

1. identify the ambiguity
2. check previous stages
3. check the original functional requirements
4. do not silently invent a major business rule

Minor technical implementation decisions may be made by the agent
when they do not change business behavior.

Major business decisions must not be invented.

MODULE 01 — ORGANIZATION & BRANCH MANAGEMENT
============================================================

PURPOSE
------------------------------------------------------------

Manage the pharmacy organization and its branches.

Example organization:

ABC Pharmacy

Branches:

Piassa Branch
Megenagna Branch

This is one organization with multiple operational branches.

------------------------------------------------------------
MAIN RECORDS
------------------------------------------------------------

Organization
Branch
Warehouse
Storage Location

------------------------------------------------------------
ACTORS
------------------------------------------------------------

System Administrator
Authorized Management users

------------------------------------------------------------
FUNCTIONS
------------------------------------------------------------

Create organization configuration.

Create branch.

Edit branch.

Activate/deactivate branch.

View branch details.

Assign warehouses to branch.

Assign users according to scope.

View branch operational information.

------------------------------------------------------------
BUSINESS RULES
------------------------------------------------------------

A branch belongs to an organization.

A warehouse belongs to a branch.

A storage location belongs to a warehouse.

Users may be assigned access to one or more branches according to
their permissions.

A user with Piassa-only scope must not access Megenagna operational
data.

Organization-level users may access multiple branches if explicitly
authorized.

------------------------------------------------------------
IMPORTANT
------------------------------------------------------------

Branch access is not the same as role.

Example:

Hana:
Role = Branch Manager
Scope = Piassa Branch

Another user:

Michael:
Role = Management
Scope = All Branches

Therefore:

Role determines what actions the user may perform.

Scope determines which records the user may access.

Expiry

Disposal
    → Stock Decrease

traceable movement.

MODULE 11 — FEFO
============================================================

PURPOSE
------------------------------------------------------------

Use First Expire, First Out for stock allocation.

------------------------------------------------------------
EXAMPLE
------------------------------------------------------------

Batch A:

Expiry = 2027-03
Available = 10

Batch B:

Expiry = 2028-05
Available = 100

Required quantity:

20

System allocation:

10 from Batch A
10 from Batch B

------------------------------------------------------------
RULE
------------------------------------------------------------

FEFO should normally be automatic.

If a user wants to bypass FEFO:

The system should apply configured warning/approval rules.

The user must not silently override FEFO.

41. EXCEPTION PRINCIPLE
============================================================

Every important module must define normal and abnormal scenarios.

Examples:

Normal:

Stock available
Payment successful
Prescription valid

Exception:

Stock insufficient
Prescription expired
Customer exceeds credit
Batch recalled
Product near expiry
FEFO conflict
Storage incompatibility
Duplicate patient
Receiving discrepancy
Unauthorized discount

The system must provide controlled handling rather than simply
crashing or silently continuing.

============================================================
42. TRANSACTION INTEGRITY
============================================================

Critical operations must be atomic where required.

Example:

Completing a sale may involve:

Create sale
→ create sale items
→ record payment
→ update inventory
→ create stock movement
→ update customer balance
→ create audit record

If a critical operation fails, the system must not leave the
database in an inconsistent state.

The backend transaction strategy defined in Stage 05 must be used.
