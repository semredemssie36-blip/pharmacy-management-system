============================================================
STAGE 06 — UX/UI ARCHITECTURE & SCREEN SPECIFICATION
PHARMACY MANAGEMENT / ERP SYSTEM
============================================================

Purpose:
Define the complete UX/UI structure of the Pharmacy Management
System before implementation.

This document defines:

- navigation
- page structure
- screens
- dashboards
- forms
- tables
- detail pages
- workflows
- buttons/actions
- status displays
- approval interfaces
- search
- filters
- notifications
- error states
- empty states
- loading states
- confirmation dialogs
- role-aware UI
- branch-aware UI
- warehouse-aware UI
- workflow-aware UI

This is NOT a visual design implementation document.

The purpose is to make sure the development agent understands what
the user should see and what the user should be able to do.

============================================================
0. CRITICAL INSTRUCTION TO THE AI DEVELOPMENT AGENT
============================================================

Before implementing any UI, the agent MUST read:

- Stage 01 — System Overview
- Stage 02 — Actors, Roles, Permissions & Data Scope
- Stage 03 — Business Rules & Workflows
- Stage 04 — Domain Model & Database Architecture
- Stage 05 — Technical Architecture & Project Foundation
- Stage 06 — UX/UI Architecture & Screen Specification

The agent MUST NOT design the interface independently without
considering the previous stages.

The UI must represent the actual business system.

Do NOT create:

- decorative dashboards with fake numbers
- buttons that do nothing
- fake approval workflows
- fake inventory updates
- fake payment completion
- fake reports
- fake notifications
- fake stock balances
- fake prescription completion

Every important UI action must correspond to a real backend
operation and business rule.

============================================================
1. CORE UX PRINCIPLES
============================================================

The application is an ERP-style pharmacy system.

It must feel like a professional business application.

The UI must prioritize:

1. clarity
2. speed
3. accuracy
4. traceability
5. safety
6. role awareness
7. branch awareness
8. workflow awareness
9. error prevention
10. auditability

The application should not feel like a simple CRUD administration
panel.

Users perform business operations.

Examples:

Storekeeper:
Receive → inspect → record batch → assign location → update stock

Pharmacist:
Open prescription → validate → review medicine → verify dispensing

Cashier:
Open POS → scan → price → discount → payment → receipt

Procurement Officer:
Review replenishment → create PO → submit → monitor approval

Manager:
Review dashboard → investigate exceptions → approve/reject where
authorized → monitor branch performance

3. TOP BAR
============================================================

The top bar should contain:

3.1 Application identity

Display:

- pharmacy/company name
- application logo
- optional current branch

Example:

ABC Pharmacy
Piassa Branch

3.2 Global search

Global search must allow authorized users to search important
business records.

Searchable areas include:

- products
- medicines
- barcode
- product code
- batches
- patients
- prescriptions
- customers
- suppliers
- invoices
- purchase orders
- stock references
- transactions

Search results should indicate the record type.

Example:

Search: "AMX-500"

Results:

PRODUCT
Amoxicillin 500mg

BATCH
AMX-2026-05

STOCK
Piassa Warehouse

The user should be able to open the appropriate record.

3.3 Branch selector

The UI must respect the user's data scope.

Example:

Current Branch:
[ Piassa Branch ▼ ]

If the user only has Piassa access:

Piassa Branch

must be available.

Megenagna should not appear.

If the user has organization-wide access:

[ All Branches ▼ ]
[ Piassa Branch ]
[ Megenagna Branch ]

The frontend must NEVER use the branch selector as a security
mechanism.

Backend authorization remains authoritative.

3.4 Notifications

Display:

- unread notification count
- recent important notifications
- notification type
- timestamp
- read/unread status
- link to related record

Examples:

LOW STOCK
Amoxicillin 500mg below reorder level.

NEAR EXPIRY
20 units of Product X expire within 60 days.

APPROVAL
Stock adjustment request requires review.

CREDIT WARNING
Customer ABC exceeded available credit.

3.5 User menu

Display:

- user name
- role
- current branch/scope
- profile
- account settings
- logout

68. UI IMPLEMENTATION RULES FOR THE AI AGENT
============================================================

The agent MUST:

1. Reuse consistent components.

2. Avoid creating separate visual patterns for every page.

3. Use reusable:
   - tables
   - forms
   - modals
   - status badges
   - alerts
   - filters
   - pagination
   - detail panels
   - approval cards

4. Keep business logic out of purely presentational components where
   possible.

5. Use permission-aware actions.

6. Use real API data.

7. Handle loading states.

8. Handle empty states.

9. Handle errors.

10. Handle permission-denied states.

11. Handle validation errors.

12. Handle business-rule conflicts.

13. Confirm destructive actions.

14. Prevent duplicate submissions.

15. Preserve traceability.

============================================================
69. WHAT THE AGENT MUST NOT DO
============================================================

DO NOT:

- invent new business workflows
- invent new roles
- invent permissions without checking previous stages
- create fake dashboard statistics
- create fake inventory calculations
- hardcode branch access
- hardcode approval authority
- automatically approve sensitive actions
- allow frontend-only authorization
- automatically restock every return
- treat quarantined stock as available
- allow expired products to be normally sold/dispensed
- bypass FEFO without appropriate rule/approval
- treat patients as customers
- treat prescriptions as normal POS transactions
- treat purchase orders as inventory
- treat payments as sales
- silently modify inventory
- silently modify financial balances
- remove audit history
- hide business-rule failures behind generic errors
