============================================================
STAGE 09 — API & BACKEND CONTRACT
============================================================

Project:
Pharmacy Management System

Purpose:
This document defines the API and backend contract between the React
frontend and the Node.js/Express backend.

This stage translates the business requirements into a controlled
backend architecture.

IMPORTANT:

The backend is the authoritative source for:

- Authentication
- Authorization
- Branch/warehouse scope
- Validation
- Business rules
- Approval rules
- Inventory changes
- Financial effects
- Prescription rules
- FEFO
- Returns
- Stock transfers
- Audit
- Notifications
- Transaction integrity

The frontend must never be trusted to enforce these rules by itself.

============================================================
3. API BASE STRUCTURE
============================================================

Use a versioned API.

Recommended:

/api/v1


Examples:

GET    /api/v1/products

GET    /api/v1/products/:id

POST   /api/v1/products

PUT    /api/v1/products/:id

DELETE /api/v1/products/:id


The exact HTTP method may vary when business actions require a dedicated
operation.

For example:

POST /api/v1/purchase-orders/:id/submit

POST /api/v1/purchase-orders/:id/approve


Do NOT implement sensitive business actions as generic unrestricted
database updates.


============================================================
4. API RESPONSE FORMAT
============================================================

Use a consistent JSON response structure.


Successful single record:

{
  "success": true,
  "data": {
    "...": "..."
  }
}


Successful list:

{
  "success": true,
  "data": [],
  "meta": {
    "page": 1,
    "perPage": 20,
    "total": 100,
    "totalPages": 5
  }
}


Successful business action:

{
  "success": true,
  "message": "Transaction completed successfully.",
  "data": {
    "...": "..."
  }
}


Error:

{
  "success": false,
  "error": {
    "code": "BUSINESS_RULE_VIOLATION",
    "message": "The selected medicine has expired.",
    "details": {}
  }
}


The exact response shape may be refined during implementation, but the
API must remain consistent.


============================================================
5. HTTP STATUS CODES
============================================================

Use appropriate HTTP status codes.

200:
Successful request.

201:
Resource created.

204:
Successful operation with no response body where appropriate.

400:
Invalid request.

401:
Unauthenticated.

403:
Authenticated but not authorized.

404:
Resource not found.

409:
Business conflict or state conflict.

422:
Validation/business validation failure where appropriate.

500:
Unexpected server error.


The backend must not expose sensitive internal error information.

POST /api/v1/auth/refresh


Login must verify:

- Credentials are valid
- Organization access is valid


The backend must establish the authenticated user context.


Authenticated request context should contain information such as:

- User ID
- Organization ID
- Role information
- Permission information
- Branch scope
- Warehouse scope


Do not trust organization, branch, or user IDs sent by the frontend when
those values can be determined from authenticated server-side context.


============================================================
7. AUTHORIZATION MODEL
============================================================

Use:

MODULE → RESOURCE → ACTION


Example:

Inventory
→ Stock Adjustment
→ Create

Inventory
→ Stock Adjustment
→ Approve

Inventory
→ Stock Adjustment
→ View


Another example:

Sales
→ Sale
→ Create

Sales
→ Sale
→ Void

Sales
→ Discount
→ Approve


Authorization must happen on the backend.


============================================================
8. DATA SCOPE
============================================================

Authorization has two dimensions:

1. What can the user do?
2. Which data can the user access?


Example:

User has:

Stock → View

But user may only have:

Piassa Branch

Therefore the user can view:

Piassa stock

but not automatically:

Megenagna stock.


The backend must apply scope restrictions to queries and mutations.

============================================================
18. FEFO API / SERVICE
============================================================

FEFO should primarily be a backend business service rather than a
frontend calculation.


Conceptual service:

allocateStock(productId, quantity, warehouseId)


The service must:

1. Find eligible stock
2. Exclude expired stock
3. Exclude unavailable stock
4. Apply configured near-expiry policy
5. Sort eligible batches by expiry
6. Allocate required quantity
7. Reserve selected stock
8. Record allocation
9. Return allocation result


The frontend must not calculate the authoritative FEFO allocation.

     ↓

Database
     ↓
Audit / Event
     ↓
Response


Sensitive transactions must not skip these layers.


============================================================
48. CONTROLLER RESPONSIBILITY
============================================================

Controllers should remain relatively thin.

Controller responsibilities:

- Receive request
- Read authenticated user
- Validate request structure
- Call appropriate service
- Return response


Controllers should NOT contain large amounts of complex business logic.


Bad:

Controller contains:

- FEFO calculation
- Inventory calculation
- Payment calculation
- Approval logic
- Audit logic
- SQL
- Notification logic


Better:

Controller
  ↓
Business Service
  ↓
Supporting services
  ↓
Repository

- Related transaction

The service must be configurable.


Do not create a separate hardcoded approval implementation for every

- Actor
- Action
- Resource
- Resource ID
- Before state where applicable
- After state where applicable
- Reason
- Timestamp
- Related transaction


Audit records should be created by backend business operations.

============================================================

Possible operations:

============================================================
55. DATABASE TRANSACTIONS
============================================================

Critical business operations must use database transactions.


Example:

Complete sale:

BEGIN

Create sale
Create sale items
Validate stock
Reserve/allocate stock
Update inventory
Create stock movement
Create payment
Update receivable
Create audit

COMMIT


If a critical operation fails:

ROLLBACK


The API must not return success if critical business effects failed.


============================================================
56. IDEMPOTENCY / DUPLICATE REQUEST PROTECTION
============================================================

Sensitive transaction APIs should consider duplicate request protection.


Example:

User clicks:

"Complete Sale"

twice quickly.


The system must not accidentally create:

2 sales

2 payments

2 inventory deductions


The implementation should use appropriate transaction/status checks and,
where necessary, idempotency mechanisms.


============================================================
57. CONCURRENCY CONTROL
============================================================

The pharmacy system may have multiple users working simultaneously.


Example:

Available stock:

10

Cashier A attempts to sell:

8

Cashier B attempts to sell:

7


The backend must prevent the system from incorrectly producing:

Available stock = -5


Inventory updates must use appropriate database concurrency/transaction
controls.


This is especially important for:

- POS
- Dispensing
- Stock transfers
- Stock adjustments
- Goods receiving

59. SECURITY RULES
============================================================

The backend must:

- Authenticate protected requests
- Authorize every sensitive operation
- Validate input
- Prevent unauthorized branch access
- Prevent unauthorized warehouse access
- Prevent SQL injection
- Protect credentials
- Protect authentication tokens/session information
- Avoid exposing sensitive internal errors
- Validate uploaded files
- Restrict sensitive operations
- Log important security/business events


Passwords must never be stored as plain text.

Prescription supporting documents/images may be uploaded where required.

- File type
- File size

- Access permission

============================================================
61. STATUS ACTION APIs
============================================================

Avoid generic:

PUT /resource/:id

for every business action.


For normal editable fields:

PUT /resource/:id


For business actions:

POST /resource/:id/submit

POST /resource/:id/approve

POST /resource/:id/reject

POST /resource/:id/complete

POST /resource/:id/cancel

POST /resource/:id/void


This makes business actions explicit and easier to authorize/audit.


============================================================
62. API SCOPE RULE
============================================================

Every query that returns branch/warehouse-sensitive information must
apply the authenticated user's scope.


Example:

GET /api/v1/inventory


The backend must determine:

Which organization?

Which branches?

Which warehouses?

Which locations?

are visible to the current user.


Do not rely on:

GET /inventory?branchId=2


as the security mechanism.


A malicious user could change:

branchId=2

to:

branchId=3


Therefore scope must be enforced server-side.
