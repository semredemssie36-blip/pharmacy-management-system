============================================================
PHARMACY ERP SYSTEM
STAGE 02 — ACTORS, ROLES, PERMISSIONS & DATA SCOPE
============================================================

PROJECT:
Multi-Branch Pharmacy Management / ERP System

IMPORTANT:
This stage defines the actors, roles, permissions, branch scope,
warehouse scope, and access-control principles of the system.

DO NOT implement the application yet.

This document is a business and architectural specification.
Implementation will happen in later stages.

============================================================
1. PURPOSE
============================================================

The Pharmacy ERP is a multi-user, multi-branch business system.

Different users must have different responsibilities.

The system must NOT use a simple rule such as:

"User is a Manager, therefore user can access everything."

Instead, access must be determined by:

USER
 +
ROLE
 +
PERMISSIONS
 +
DATA SCOPE

The permission system must be configurable and extensible.

============================================================
2. CORE ACCESS-CONTROL MODEL
============================================================

The system should conceptually evaluate access as:

USER
 ↓
ROLE(S)
 ↓
PERMISSIONS
 ↓
DATA SCOPE
 ↓
REQUESTED RESOURCE
 ↓
ACTION
 ↓
ALLOW / DENY / APPROVAL REQUIRED

Example:

Hana
Role:
Branch Manager

Scope:
Piassa Branch

Permission:
Inventory → Stock Adjustment → Create

Result:

Hana can create a stock adjustment for Piassa within her
authorized scope.

She should not automatically create an adjustment for
Megenagna.

============================================================
3. ROLE != DATA SCOPE
============================================================

This is one of the most important rules in the system.

ROLE answers:

"What type of work can this user perform?"

DATA SCOPE answers:

"Which organization's data can this user perform that work on?"

Example:

Hana:
Role = Branch Manager
Scope = Piassa Branch

Bethlehem:
Role = Branch Manager
Scope = Megenagna Branch

Both have the same role.

But they do not necessarily have access to the same branch data.

============================================================
4. ORGANIZATION STRUCTURE
============================================================

Organization:

ABC Pharmacy

Branches:

Piassa
Megenagna

Example:

ABC Pharmacy
│
├── Piassa Branch
│   └── Main Warehouse
│
└── Megenagna Branch
    └── Main Warehouse

A user may have:

- Organization-wide scope
- Multiple branch scope
- One branch scope
- Warehouse scope

The exact scope assigned to a user must be configurable.

============================================================

The system must support at least:

1. System Administrator
2. Branch Manager
3. Pharmacist
4. Pharmacy Technician / Dispensing User

18. ACTION TYPES
============================================================

The permission system should support common actions such as:

- View
- Search
- Create
- Update
- Delete where safe
- Submit
- Approve
- Reject
- Cancel
- Complete
- Verify
- Dispense
- Receive
- Dispatch
- Return
- Refund
- Export
- Print

Not every resource needs every action.

Sensitive actions must have explicit permissions.

============================================================
19. DELETE PRINCIPLE
============================================================

Business transactions should generally not be physically deleted
after they become operational records.

Examples:

A completed sale should not simply be deleted.

A completed purchase receipt should not simply be deleted.

A completed stock movement should not simply be deleted.

Instead, appropriate correction/reversal/return/void workflows
should be used.

Deletion rules will be defined in later business-rule stages.

============================================================
20. DATA SCOPE
============================================================

Data scope must be supported independently from role.

Possible scope levels:

1. Organization
2. Branch
3. Warehouse
4. Storage location where required

Example:

Hana
Role = Branch Manager
Scope = Piassa

Hana can access Piassa records according to her permissions.

Hana should not automatically access Megenagna records.

============================================================
21. CROSS-BRANCH ACCESS
============================================================

Cross-branch access must be explicit.

Example:

Piassa Branch Manager wants to transfer stock from Megenagna.

The user may see only the information necessary for the
authorized transfer workflow.

The system should NOT automatically give full Megenagna access
just because a transfer exists.

Possible approach:

Hana may:

- Create transfer request
- Select authorized destination/source
- View required product/quantity information
- Track transfer status

But may not:

- Browse all Megenagna patient records
- Browse all Megenagna sales
- Browse unrelated Megenagna financial information

unless explicitly authorized.

============================================================
22. APPROVAL AND PERMISSION ARE DIFFERENT
============================================================

Permission means:

"Can this user perform or initiate this action?"

Approval means:

"Does this action require another authorized person to approve
it before it becomes effective?"

Example:

Storekeeper:
Permission = Create Stock Adjustment

But:

Stock Adjustment:
Approval Required = YES

Therefore:

Storekeeper
 ↓
Creates adjustment
 ↓
Submits
 ↓
Branch Manager / authorized approver
 ↓
Approves
 ↓
Inventory changes

Having "Create" permission does NOT mean having "Approve"
permission.

============================================================
23. SEPARATION OF DUTIES
============================================================

The system should support separation of duties for sensitive
operations.

Examples:

Purchase Order:
Procurement creates
        ↓
Authorized approver approves
        ↓
Storekeeper receives

Stock Adjustment:
Storekeeper creates
        ↓
Authorized approver approves
        ↓
Inventory updated

Dispensing:
Technician prepares
        ↓
Pharmacist verifies
        ↓
Dispensing completed

This prevents one user from silently performing an entire
sensitive process alone where approval is required.

============================================================
24. PERMISSION CHECKING
============================================================

Permission checks must exist at the backend/API level.

The frontend must NOT be the only security mechanism.

Example:

Hiding a button:

"Approve Adjustment"

is useful for UX.

But the backend must also verify:

Does this authenticated user have permission to approve this
adjustment?

The system must enforce authorization on the server.

============================================================
25. DATA-SCOPE CHECKING
============================================================

Permission alone is not sufficient.

The backend must also check the user's authorized data scope.

Example:

User:
Hana

Permission:
Inventory → Stock → View

Scope:
Piassa

Request:
View Megenagna stock

Result:
DENIED

Even though Hana has inventory-view permission, her data scope
does not include Megenagna.

============================================================
26. AUDIT REQUIREMENT
============================================================

Important permission-sensitive actions must eventually produce
audit records.

Examples:

- User created
- Role changed
- Permission changed
- Branch scope changed
- Warehouse scope changed
- Approval performed
- Permission denied
- Sensitive action overridden

Detailed audit implementation will be handled in a later stage.

============================================================
27. SECURITY PRINCIPLE
============================================================

Use least privilege.

A user should receive only the permissions and data scope
necessary for their job.

Do NOT use:

"Give everyone administrator access so development is easier."

Temporary development shortcuts must not become the final
business architecture.

The system must allow new roles.

Examples of possible future roles:

============================================================
30. FRONTEND AUTHORIZATION
============================================================

The frontend should use permissions to control the user
experience.

Examples:

If user does not have:

Inventory → Stock Adjustment → Create

Then:

"New Adjustment" button should not normally be displayed.

If user does not have:

Reports → Financial → View

Then the financial report should not be displayed.

However:

Frontend hiding is NOT security.

Backend authorization remains mandatory.

============================================================
31. BACKEND AUTHORIZATION
============================================================

Every protected API operation must verify:

1. Authentication
2. Permission
3. Data scope
4. Resource ownership/access where applicable
5. Approval state where applicable

Example:

POST /stock-adjustments

Backend checks:

User authenticated?
        ↓
Has inventory adjustment create permission?
        ↓
Is branch within user's scope?
        ↓
Is warehouse within user's scope?
        ↓
Are required fields valid?
        ↓
Is approval required?
        ↓
Create pending adjustment

============================================================
32. NO BUSINESS BYPASS
============================================================

The system must prevent users from bypassing normal business
workflows through APIs.

For example:

A user should not be able to directly send:

"stock = 500"

to an API and bypass stock movement logic.

Inventory should be changed through authorized business
operations.

Likewise:

- Completed sale cannot be silently edited
- Approved purchase order cannot be silently modified
- Approved adjustment cannot be silently changed
- Verified dispensing cannot be silently changed

Correction workflows must be designed later.

34. CONSISTENCY REQUIREMENT
