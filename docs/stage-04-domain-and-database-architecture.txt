IMPORTANT:
This stage defines the conceptual domain model and database
architecture of the Pharmacy ERP.

DO NOT implement the database yet.

DO NOT generate migrations yet.

The purpose of this stage is to establish what information the

business concepts must remain separate.

============================================================

============================================================

The database must represent the real pharmacy business.

It must support:

- Multi-branch organization
- Users and roles
- Permissions
- Branch and warehouse scope
- Products and medicines
- Suppliers
- Customers
- Patients
- Prescribers
- Procurement
- Purchase orders
- Goods receiving
- Batch and expiry
- Inventory
- Stock movements
- FEFO

- Notifications
- Reporting
- Pricing
- Discounts
- Credit/receivables
- Supplier payables
- Other configured financial information

The database must support the business workflows defined in
Stage 03.

============================================================
2. DATABASE DESIGN PRINCIPLE
============================================================

Do NOT design the database by simply creating one table for
every screen.

A UI page is not automatically a database entity.

Instead, design around:

BUSINESS DOMAIN
    ↓
BUSINESS ENTITY
    ↓
BUSINESS RELATIONSHIP
    ↓
BUSINESS TRANSACTION
    ↓
BUSINESS EFFECT

Example:

Purchase Order
    ↓
Purchase Order Items
    ↓
Goods Receipt
    ↓
Goods Receipt Items
    ↓
Batch
    ↓
Inventory
    ↓
Stock Movement

============================================================
15. INVENTORY LOCATION PRINCIPLE
============================================================

The same product may exist in multiple locations.

Example:

Amoxicillin 500mg

Piassa Warehouse:
Batch A:
100

Piassa Pharmacy:
Batch A:
20

Megenagna Warehouse:
Batch B:
200

These are not one undifferentiated quantity.

The system must preserve location context.

============================================================
16. STOCK MOVEMENT DOMAIN
============================================================

Stock movement is one of the most important transactional
entities.

Every important inventory change should have a movement record.

Possible movement types:

- Opening balance
- Purchase receipt
- Sale
- Dispensing
- Customer return
- Supplier return
- Transfer in
- Transfer out
- Adjustment
- Damage
- Expiry
- Recall
- Disposal

A stock movement should conceptually contain:

- Product
- Batch
- Quantity
- Movement type
- Source
- Destination where applicable
- Branch
- Warehouse
- Location
- Reference transaction
- User
- Date/time
- Reason where applicable

Stock movement provides inventory history.

============================================================
17. STOCK MOVEMENT PRINCIPLE
============================================================

Do not rely only on the current inventory quantity.

The system should preserve transaction history.

Example:

Current quantity:
100

But history may show:

+200 Purchase Receipt
-50 Sale
-30 Dispensing
-20 Transfer Out

The movement history explains how the current quantity was
produced.

============================================================
18. FEFO DOMAIN
============================================================

FEFO is primarily a business allocation rule based on batch
expiry.

The database must preserve enough information to determine:

- Which batches exist
- Which batches are available
- Expiry date
- Quantity
- Location
- Status

The system should be able to identify the earliest eligible
expiry batch.

FEFO itself should not be treated as merely a UI sorting option.

It affects actual stock allocation.

49. HISTORICAL DATA PRINCIPLE
============================================================

Historical transactions must not be destroyed simply because
master data changes.

Example:

Product selling price today:
150 ETB

Old sale:
120 ETB

The old sale must continue showing:

120 ETB

Changing the product's current price must not rewrite the
historical transaction.

Similarly:

- Old customer information
- Old supplier information
- Old product information
- Old exchange rates
- Old discounts

must not incorrectly rewrite completed historical transactions.

============================================================
51. DATABASE TRANSACTION INTEGRITY
============================================================

Some business operations affect multiple records.

Example:

Complete Sale:

1. Create/update sale
2. Create sale items
3. Allocate stock
4. Create stock movement
5. Record payment
6. Update financial state
7. Create audit record

These operations must be handled atomically where appropriate.

If the operation fails halfway, the system must not leave
inventory and financial records inconsistent.

Technical database transactions will be implemented later.

============================================================
52. SOFT DELETE / ARCHIVE PRINCIPLE
============================================================

Important master data may need to be deactivated rather than
physically deleted.

Examples:

- Product
- Supplier
- Customer
- User
- Branch
- Warehouse

Historical transactions must continue to reference historical
records.

Business transactions should generally not be physically
deleted after completion.

Correction should use appropriate business workflows.

============================================================
53. UNIQUE IDENTIFIERS
============================================================

Important business entities should have unique identifiers.

Examples:

- Product code
- Barcode where applicable
- Purchase Order number
- Goods Receipt number
- Sale number
- Prescription number
- Dispensing number
- Transfer number
- Adjustment number
- Return number
- Payment reference
- Recall number

Identifier generation must avoid collisions.

============================================================
54. DATA VALIDATION PRINCIPLE
============================================================

Database constraints should protect critical business rules.

Examples:

- Required fields
- Valid references
- Unique identifiers
- Positive quantities where appropriate
- Valid dates
- Valid relationships
- Valid statuses
- Foreign key integrity

Application validation is required too.

Database constraints are an additional protection layer.

============================================================
55. DO NOT OVER-NORMALIZE WITHOUT REASON
============================================================

The database should be properly normalized for business data,
but the implementation should remain practical.

Do not create dozens of meaningless tables simply because
normalization is theoretically possible.

Every table should represent a meaningful business concept,
support a relationship, or provide a necessary technical
function.

============================================================
56. DO NOT DENORMALIZE WITHOUT REASON
============================================================

Do not duplicate important business values unnecessarily.

If a value must be duplicated for historical correctness,
reporting performance, or transaction snapshots, that should be
an explicit design decision.

Example:

A sale item may preserve the actual unit price used at the time
of sale even though the product has a current price.

This is intentional historical data, not accidental duplication.

============================================================
57. DATABASE DESIGN REVIEW REQUIREMENT
============================================================

Before implementation, the database design must be reviewed
against:

Stage 01:
System Overview

Stage 02:
Actors, Permissions and Data Scope

Stage 03:
Business Rules and Workflows

The database must support all important workflows.

If a business workflow cannot be represented by the proposed
domain model, the design must be revisited before coding.

59. RECALL TRACEABILITY
============================================================

The database should make it possible, where available, to answer:

"Where is this batch now?"

and:

"Where did this batch go?"

For example:

Batch:

60. INVENTORY TRACEABILITY
============================================================

For a stock quantity, the system should be able to identify:

- Product
- Batch
- Expiry
- Location
- Current state
- Source
- Movement history

This supports:

- FEFO
- Recall
- Expiry
- Returns
- Auditing
- Stock reconciliation

============================================================
61. DATABASE DESIGN ANTI-PATTERNS
============================================================

DO NOT create a design where:

1. Stock is directly overwritten without movements.

2. Purchase orders directly increase inventory.

3. Completed sales can be freely edited.

4. Customer and patient are forced into one entity without
   considering their different business meanings.

5. Branch managers automatically see every branch.

6. Approval is represented only by a boolean such as:
   approved = true

without preserving approval history.

7. Audit is only:
   updated_at

8. Batch and expiry information are ignored.

9. FEFO exists only as a frontend sorting option.

10. Financial transactions are disconnected from their source
    business transactions.

11. Historical transaction prices change when current prices
    change.

12. Returns simply delete or reverse records without preserving
    return history.

63. DATABASE IMPLEMENTATION PRINCIPLE
============================================================

When the implementation stage begins:

1. Review this domain model.
2. Identify final entities.
3. Identify attributes.
4. Identify relationships.
5. Identify primary keys.
6. Identify foreign keys.
7. Identify indexes.
8. Identify unique constraints.
9. Identify status values.
10. Identify audit requirements.
11. Identify transaction boundaries.
12. Review against all business workflows.
13. Only then create migrations.

DO NOT allow the AI agent to generate a random database from
the UI screens.

============================================================
66. FINAL DOMAIN PRINCIPLE
============================================================

The database is not simply storing screens.

It is storing the history and current state of the pharmacy
business.

Therefore:

MASTER DATA
    ↓
BUSINESS TRANSACTIONS
    ↓
BUSINESS EFFECTS
    ↓
INVENTORY / FINANCE
    ↓
APPROVAL
    ↓
AUDIT
    ↓
REPORTING

must remain connected.

The database must make it possible to answer:

- What happened?
- Who did it?
- When did it happen?
- Which branch?
- Which warehouse?
- Which product?
- Which batch?
- Which patient/customer?
- Which supplier?
- Which transaction?
- Who approved it?
- What changed?
- What is the current state?
