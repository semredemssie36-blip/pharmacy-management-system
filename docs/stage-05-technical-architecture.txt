                      ▼

                      ▼

============================================================
12. CONTROLLER RESPONSIBILITY
============================================================

Controllers should be thin.

Controller responsibilities:

- Receive request
- Obtain authenticated user
- Call validation
- Call service
- Return response

Controllers should NOT contain large amounts of business logic.

Avoid:

Huge controller methods containing:

- stock calculations
- approval rules
- payment calculations
- FEFO logic
- database queries
- audit logic

Those belong in appropriate services/domain logic.

16. AUTHENTICATION
============================================================

Users must authenticate before accessing protected system
features.

Authentication must establish the current user identity.

The system should be designed to support secure session/token
handling.

The exact authentication mechanism must be selected during
implementation based on security requirements.

The agent must NOT invent an insecure authentication shortcut.

============================================================
17. AUTHORIZATION
============================================================

Authentication answers:

"Who are you?"

Authorization answers:

"What are you allowed to do?"

The system must implement:

USER
→ ROLE
→ PERMISSIONS
→ DATA SCOPE

Example:

Hana
Role:
Branch Manager

Scope:
Piassa

Hana should not automatically access Megenagna data.

============================================================
18. DATA SCOPE
============================================================

Authorization must consider both:

ACTION PERMISSION

and

DATA SCOPE

Example:

Permission:
inventory.stock.view

Scope:
Piassa

This means:

User can view inventory
BUT only within Piassa scope.

A user may have organization-wide scope if explicitly
configured.

============================================================
19. BACKEND AUTHORIZATION RULE
============================================================

Never trust the frontend for authorization.

Bad:

Frontend hides:
"Delete"

but backend accepts:
DELETE /api/products/123

Good:

Backend verifies:

1. User authenticated?
2. User has required permission?
3. User has access to this branch?
4. User has access to this warehouse?
5. Operation allowed for current transaction status?

Only then execute.

============================================================
20. VALIDATION
============================================================

Validation should occur at multiple levels.

Frontend:
User experience validation.

Backend:
Authoritative validation.

Database:
Integrity constraints.

Example:

Frontend:
Quantity must be positive.

Backend:
Quantity must be positive and stock rules must allow it.

Database:
Quantity and relationships must satisfy constraints.

============================================================
21. BUSINESS VALIDATION
============================================================

Technical validation is not enough.

Example:

quantity = 10

Technically valid.

But business validation may say:

Available stock = 5

Therefore:

Transaction must be rejected or handled as an exception.

Business validation belongs in the backend service/domain layer.

============================================================
22. DATABASE TRANSACTIONS
============================================================

Critical operations involving multiple database changes must use
database transactions.

Example:

Complete Sale:

BEGIN TRANSACTION

1. Validate sale
2. Validate stock
3. Allocate batch
4. Create sale
5. Create sale items
6. Create stock movements
7. Update inventory
8. Record payment
9. Record audit

COMMIT

If a critical operation fails:

ROLLBACK

This prevents inconsistent state.

============================================================
23. EXAMPLE: SALE TRANSACTION
============================================================

A completed sale may involve:

Sale
Sale Items
Batch Allocation
Inventory
Stock Movement
Payment
Receipt
Audit

These related changes should be coordinated as one business
operation.

The system must not create a payment while leaving inventory
unchanged due to an unnoticed failure.

============================================================
24. FEFO IMPLEMENTATION PRINCIPLE
============================================================

FEFO must be implemented on the backend.

The frontend may display suggested batches.

But the backend must determine whether the requested allocation
is valid.

The backend should:

1. Find eligible stock
2. Exclude expired stock
3. Exclude blocked/quarantined/recalled stock
4. Order eligible batches by expiry
5. Allocate according to FEFO
6. Support authorized override
7. Record allocation
8. Record audit when required

They must not be treated as the same system.
