============================================================
STAGE 10 — IMPLEMENTATION PLAN & MODULE DEPENDENCY
============================================================

Project:
Pharmacy Management System

Purpose:
This document defines the exact order in which the Pharmacy Management
System will be implemented.

This is the final planning stage before actual implementation begins.

The implementation must follow the business architecture defined in
Stages 01–09.

IMPORTANT:

The system must NOT be built as one giant CRUD generation task.

Implementation must proceed in controlled vertical slices.

Each slice should become:

- Database
- Backend
- API
- Authorization
- Business rules
- Frontend
- Validation
- Testing

before moving too far into the next dependent module.


============================================================
1. IMPLEMENTATION PRINCIPLE
============================================================

The project is a real Pharmacy ERP-style system.

It is NOT:

- A simple CRUD application
- A collection of unrelated pages
- A frontend prototype
- A collection of fake dashboards
- A collection of disconnected forms

The implementation must preserve:

Business process
        ↓
Business rules
        ↓
Database
        ↓
Backend service
        ↓
API
        ↓
Frontend
        ↓
User action
        ↓
Business effect
        ↓
Audit / notification

============================================================

Expiry:

Near-expiry and expired stock must be identifiable.


Recall:

Affected batch
→ Identify stock
→ Identify locations
→ Identify affected customers/patients where traceability exists
→ Notification
→ Return/reconciliation
→ Completion


These are different business processes.


Do not merge them into one generic "bad stock" feature.

============================================================
27. BUSINESS TEST SCENARIOS
============================================================

Scenario 1:

User attempts to access another branch.

Expected:

Access denied.


Scenario 2:

User attempts to sell expired medicine.

Expected:

Transaction rejected.


Scenario 3:

Prescription quantity = 20.

User attempts to dispense 25.

Expected:

Transaction rejected.


Scenario 4:

Stock = 10.

User attempts to sell 15.

Expected:

Transaction rejected unless a valid business rule explicitly permits
another behavior.


Scenario 5:

PO approved.

Expected:

Inventory unchanged.


Scenario 6:

Goods receipt completed.

Expected:

Inventory increases.


Scenario 7:

Stock adjustment requires approval.

Expected:

Stock does not change before required approval.


Scenario 8:

Customer return is inspected and found unsuitable.

Expected:

Stock does not become saleable.


Scenario 9:

Recall is created for batch X.

Expected:

System identifies affected stock and traceable recipients where data
exists.


Scenario 10:

Two users attempt to sell the same limited stock.

Expected:

Backend prevents incorrect over-allocation.

42. DO NOT BUILD EVERYTHING AT ONCE
============================================================

The coding agent must work in controlled increments.


Bad approach:

"Build the entire pharmacy ERP now."


This creates:

- Missing business rules
- Broken dependencies
- Inconsistent permissions
- Incorrect inventory
- Fake pages
- Difficult debugging
- Large numbers of hidden errors


Preferred approach:

"Implement the Product Master vertical slice."

Test it.

Then:

"Implement Inventory Foundation."

Test it.

Then:

"Implement Procurement."

Test it.


Continue progressively.

44. OPEN CODE IMPLEMENTATION RULE
============================================================

OpenCode must work from the stage documents.


Before implementing a module:

1. Read all previous relevant stages.
2. Identify the module's dependencies.
3. Identify business rules.
4. Identify actors.
5. Identify permissions.
6. Identify scope.
7. Identify statuses.
8. Identify approval requirements.
9. Identify inventory effects.
10. Identify financial effects.
11. Identify audit requirements.
12. Identify notification requirements.
13. Implement the module.
14. Test it.
15. Report what was implemented.


OpenCode must NOT silently invent missing requirements.
